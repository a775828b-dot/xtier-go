# Y900：Dory 4B 整步跑在 Hexagon NPU 上（2026-11-08）

[回到文档目录](../README.md) · 做法见 [npu.md](../npu.md)

设备：联想 Y900（Snapdragon 8 Elite SM8750P，Hexagon V79，16 GB）。导出：ExecuTorch v1.5.1 + QAIRT 2.37，16 位激活、
4 位权重块（16 个一块）、8 位 KV，从 BF16 版量化。引擎、插件和测试工具都是本仓库的（`npu/`、`tools/npu_et/`）。

## 结论

- Dory 4B 全量跑通：切 4 片（两轮循环展开、各一份权重），1–3 秒加载，回退、快照、换档都和逐个算一致；接口检查
  `tests/api_check.py` 对平板上的 NPU 引擎全部通过，DSH Go X 能连上。
- 速度（4K 档，引擎在平板上，生成 700 个 token）：**1 次循环 prefill 约 400 tok/s，decode 14.4**，配提示查找后改代码这类
  照抄多的任务 51.5、以思考为主的任务 16.9；**2 次循环 prefill 280–290、decode 9.4**（提示查找 12–15）。
- 精度：一开始 prefill 图 NLL 比参考高 0.33 nat，查下来是**导出把新 V 和 V 缓存量化成了不同的编码**（每层的 V 缓存是
  下一层新 V 的编码），插件原样写回缓存，缓存里的 V 被放大 / 缩小最多 7 倍。插件改成按编码映射写回（`kvmap`）后，prefill
  和逐个算都和 BF16 参考持平（2 次循环 NLL 1.093 / 1.096，参考 1.104）。
- 长档位：拼接写法（缓存和新行拼起来、K / V 按 q 头复制）每步要把整个缓存搬好几遍，1 次循环 32K decode 只有 2.4 tok/s。
  查出两个原因并修掉：插件的共享内存把缓存算了 3 遍、DSP 映射不下，QNN 每步拷贝（修后 32K 3.6 tok/s）；HTP 把跨头广播的
  RoPE 乘法编错，原地读缓存的写法因此精度很差，RoPE 表先复制成完整形状后精度回到和拼接写法一样。但原地读只在 8K 以内占优：4K / 8K decode 每步 64 / 80 ms，32K 680 ms（HTP 对大的分组乘法调度很差），
  所以 32K 档仍用拼接写法（280 ms）。
- DSH Go X：标准模式的基础提示（系统提示 + 工具定义）16,071 token，**内置的极简模式 4,202 token**；前缀缓存修好后每轮只算
  新增的部分（之前 DSH 不回传思考，每轮从零算）。极简模式里跑一个简单工具任务 3 分钟：首轮 4.2K 提示约 12 秒（4K 档，然后搬到 8K），回答约 15 tok/s，工具
  来回每轮 1–2 秒（缓存命中 85%），其中约 1 分钟是 DSH 起会话标题的请求。DSH 在安卓上没有沙箱后端，「工作区内修改」
  权限下命令被拒绝执行（DSH 的环境问题，模型的工具调用本身正常）。

引擎（`xtg-server --opt backend=npu`，温度 0，各生成 700 个 token；投机解码是提示查找，最多 7 个草稿）：

| 配置 | 改代码（照抄多）prefill / decode | 解释代码（主要在思考）prefill / decode |
|---|---|---|
| 1 次循环 + 投机 | 440 / 51.5（每次前向 3.8 个） | 387 / 16.9（1.2 个） |
| 1 次循环 | 409 / 14.4 | 388 / 14.4 |
| 2 次循环 + 投机 | 289 / 14.7（1.6 个） | 276 / 11.8（1.3 个） |
| 2 次循环 | 292 / 9.4 | 278 / 9.4 |

- decode 受带宽限制：2 次循环每 token 读约 3.5 GB（权重 3.2 + KV），HTP 实际约 33–40 GB/s。8 行的 decode 图算 1 个比 1 行图
  慢 24%，算 8 个只比算 1 个多 15%，所以投机解码打开时用 8 行图。
- 1 次循环每 token 少读约 1/3 的权重，代价是能力（官方 SWE-bench 59.5 → 50.3）。

### 长档位（1 次循环，`npu_test`，1K 提示）

| 档位 · 写法 | prefill | decode 每步 | NLL（2K 文本） |
|---|---:|---:|---:|
| 4K · 拼接 | 478 tok/s | 72 ms（14.2 tok/s） | 1.016 |
| 20K · 拼接（修共享内存前 / 后） | 73 / 85 | 247 / 150 ms | 1.016 |
| 32K · 拼接（修共享内存前 / 后） | 50 / 54 | 418 / 280 ms | 1.019 |
| 4K · 原地读 | 342 | 64 ms（15.5） | 1.020 |
| 8K · 原地读 | 162 | 80 ms（12.5） | 1.020 |
| 32K · 原地读 | 35 | 680 ms（1.45） | 1.012 |

- 静态图每步都按整个档位算（被掩的槽也读）。拼接写法每多 1K 上下文每步多约 11 ms（修共享内存后约 7 ms），搬的数据是必要的
  十几倍：4K 时中间结果在 VTCM 里，长档位全走 DDR。
- 共享内存：插件按"缓存 + 每张图的全部 I/O"分配，而图的输入里本来就有缓存，结果是缓存的 3 倍（20K 1.34 GB、32K 2.02 GB），
  加上约 3 GB 权重超出 DSP 能映射的范围，QNN 报 `Failed to register memHandles`，映射不上的张量每步拷贝。
- 换档 4K → 20K 1.7 秒、4K → 32K 2.4 秒；搬到 20K 后续写和不搬时 31 个 token 全同，搬到 32K 后只有前 8 个相同，没有再
  细查（可能是两张图数值上的小差别：Dory 前两名常只差零点几，贪心容易走到别的分支）。

## 精度

同一段 2048 token 的 agent 文本（S1 轨迹，28K 会话的最后一段），逐位置的下一 token NLL 对 BF16 参考实现
（`reference/dory_ref.py`）：

| | NLL | |
|---|---:|---|
| BF16 参考 | 1.104 | |
| NPU 2 次循环，prefill 图（64 行一块） | **1.093** | 修复前 1.434 |
| NPU 2 次循环，decode 图逐个算 | 1.096 | 修复前 1.167 |
| NPU 1 次循环，prefill 图 | 1.016 | 修复前 1.325（1 次循环的参考没算） |
| CPU 模拟：只量化 KV 到 8 位 | 1.106 | argmax 一致 96.5% |
| CPU 模拟：4 位分块权重 | 1.018 | argmax 一致 86.6% |

这段文本是 NVFP4 版自己生成的，4 位量化后的 NLL 反而可能比 BF16 低，所以只能说「和参考持平」；量化本身的损失按 CPU 模拟
看主要来自 4 位权重（argmax 一致率 87%），8 位 KV 几乎没有影响。批量验证 8 个 token 和逐个算 47 行里 44 行一致。

修复前的误差是怎么查到的：同一行单独算时 prefill 图和 decode 图逐位相同，块里一起算的行越多误差越大；`npu_test … kvcmp`
显示第 0 层写进缓存的 K / V 逐字节相同、往后逐层变大；`kv_enc_check.py` 对比上下文二进制里的张量编码，发现 K 的输出和缓存
编码一致，而**每个 V 缓存都是下一层新 V 的编码**（ExecuTorch 的 KV 量化注解造成）。插件现在写回缓存时按两个编码做字节映射
（`NAME.kvmap.json`，导出脚本自动生成），不用重新导出。

## 内存

| 导出 | .pte | 引擎上线后系统可用内存少了 |
|---|---:|---:|
| 2 次循环 4K | 3.99 GB | （待测） |
| 1 次循环 4K | 2.93 GB | 3.7 GiB（10.5 → 6.8） |

HTP 的权重在 DMA 缓冲里，不算进进程 RSS（进程只有 0.2 GiB）；`.pte` 只映射不锁（锁的话会多占一份）。

## 做法里踩到的坑

- QAIRT 2.47 + ExecuTorch 1.5.1：切过片的模型一执行 DSP 就崩（官方 Qwen3-1.7B 也一样），换 2.37 正常。
- 循环共用一份权重时，HTP 把被两个算子读的权重变成每步重算的 DDR 张量，循环那一片超过 3.5 GiB 的上下文上限 → 展开。
- GQA 的 `repeat_kv` 在 32K 时让 HTP 把每个 KV 头复制 4 份（输入片 decode 每步读 1.5 GB、prefill 每块 6.9 GB）→ 4 个 q 头
  叠在行上、缓存原地读（`split`）。第一版 NLL 1.61 / 1.76（`cat` 1.016）：后端的 MHA→SHA 拆头只认得 `cat` 那种图，`split`
  不拆头，而第一片之后 RoPE 的 cos / sin 是图的输入，HTP 把它们跨头广播的乘法编错（编译日志 “elementwise op applied to
  mismatched shapes”）。把 `cat` 的拆头关掉也一样坏（tiny 上 argmax 和正常的 `cat` 只有 37% 一致）。RoPE 表先复制成 q / k 的
  完整形状后 tiny 回到 96.5%。只分组不拆缓存的写法在设备上 prefill 报 1003。
- 共享内存分了缓存的 3 倍，长档位 DSP 映射不下、QNN 每步拷贝（见上）。
- 前缀缓存：Dory 的模板把历史里的思考去掉，客户端回传的历史在上一轮提示结尾前几个 token 就和缓存分叉；生成之后滑窗环
  退不回去（只有 64 个余量），快照又在分叉点之后，于是每轮从零算。现在恢复分叉点之后的快照、再在环的余量内退回去。
- Dory 的注意力分数到几百，掩码用 masked softmax（行最小值 −20）；加 −255 的常规掩码会让被掩的 key 胜出。

## 复现

服务器上导出见 [npu.md](../npu.md)；平板上：

```bash
npu_test model.pte prompt.bin 128 16          # 测速 + 回退一致性
npu_test model.pte prompt.bin verify 64       # 批量验证一致性和每步耗时
npu_test model.pte prompt.bin score out.txt   # 逐位置打分（XTG_SCORE_STEP=1 走 decode 图），再跑 compare_score.py
npu_test a-c32k.pte prompt.bin grow a-c96k.pte 64   # 换档
```
